# Архитектура: MATSim AI Toolkit

Каркас, который даёт LLM-агенту (Claude) надёжно работать с транспортными моделями MATSim.

## Принцип

LLM — оркестратор, а не парсер. Агент рассуждает на уровне транспортной логики
(«закрыть мост, проверить modal split»), а грязную работу (XML, запуск, парсинг)
делают типизированные инструменты. Агент всегда получает компактный JSON, никогда —
сырой XML на сотни МБ.

## Четыре слоя

```
┌──────────────────────────────────────────────────────────────┐
│ 1. ЗНАНИЯ        skills/transport-modeling/                   │
│    ~60 правил из 4 источников. Агент знает КАК правильно.     │
├──────────────────────────────────────────────────────────────┤
│ 2. БЕЗОПАСНОСТЬ  hooks/validate_matsim.py                     │
│    PreToolUse contract-first валидация перед записью XML.     │
│    Ловит ошибки ДО того как они попадут в модель.            │
├──────────────────────────────────────────────────────────────┤
│ 3. ДЕЙСТВИЯ      tools/*.py                                   │
│    summarize / metrics / run / modify. Чистый Python stdlib. │
│    Каждый инструмент: вход = пути/параметры, выход = JSON.   │
├──────────────────────────────────────────────────────────────┤
│ 4. ОБРАТНАЯ СВЯЗЬ  парсинг штатных output-CSV MATSim         │
│    scorestats / modestats / traveldistancestats / analysis/  │
│    Java-хук НЕ нужен — MATSim пишет метрики сам.             │
└──────────────────────────────────────────────────────────────┘
```

## Чем отличается от «классической» схемы (Python MCP → Java wrapper → сокеты)

| Узел | «Классика» | Здесь | Почему |
|------|-----------|-------|--------|
| Метрики | Свой Java `IterationEndsListener` пишет JSON | Парсим штатные CSV MATSim | MATSim уже всё пишет сам. Меньше кода, ноль пересборки. |
| Слой действий | Python FastAPI + Java wrapper + файловый обмен | Python CLI на stdlib | Для соло-разработки в Claude Code межпроцессный мост — оверкилл на старте. |
| Async-симуляция | Веб-хуки + пуш-уведомления | Нативный `run_in_background` Claude Code | Среда уже умеет будить агента по завершении фоновой задачи. |
| Знания агента | (отсутствует) | Слой skill | Без него агент выдумывает значения — проверено на евалах. |

MCP-обёртка добавляется на слое 3 **после** того как CLI-инструменты доказали пользу,
а не до. MCP оправдан когда нужны переносимые typed-инструменты на много сессий
или интеграция в Claude Desktop / другие хосты.

## Контракты данных

Инструменты возвращают компактный JSON. Примеры схем:

### Сводка сети (`summarize --network`)
```json
{
  "network_id": "shamalgan",
  "nodes": 1840,
  "links": 4210,
  "freespeed_ms": {"min": 2.78, "max": 33.33, "suspicious_over_50ms": 0},
  "capacity_vph": {"min": 300, "max": 4000},
  "road_types": {"residential": 1200, "primary": 340, "...": 0},
  "warnings": []
}
```

### Метрики симуляции (`metrics <output_dir>`)
```json
{
  "iterations": 10,
  "score": {"initial": 106.6, "final": 121.3, "delta": 14.7},
  "modal_split_final": {"car": 0.49, "pt": 0.18, "walk": 0.33},
  "modal_split_initial": {"car": 0.55, "pt": 0.16, "walk": 0.28},
  "travel_distance_avg_m": {"initial": 8120, "final": 7640}
}
```

## Принципы безопасности (contract-first)

1. Любое изменение модели проходит валидацию на стороне Python **до** записи в файл.
2. Параметры из LLM проверяются на типы и диапазоны (capacity > 0, freespeed в м/с и т.д.).
3. Read-only инструменты физически не могут изменить модель.
4. Запуск симуляции ограничен по итерациям для интерактивного цикла (длинные прогоны — в фон).
