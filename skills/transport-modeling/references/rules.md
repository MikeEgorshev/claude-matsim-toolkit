## Категория A: Алгоритм MATSim (коэволюция)

| # | Правило | Источник | Уверенность |
|---|---------|----------|------------|
| A1 | Каждый агент ведёт **набор планов** (по умолчанию до 5). Каждую итерацию один план исполняется в mobsim и получает score. | [M] p.99, §14.1 | Высокая |
| A2 | Replanning: (1) удалить план с худшим score если память полна, (2) скопировать + мутировать план для части агентов (инновация), (3) остальные агенты выбирают план по score. | [M] p.99 | Высокая |
| A3 | Инновационные стратегии нужно **отключить** ближе к концу итераций (`fractionOfIterationsToDisableInnovation`), чтобы дать score сойтись. | [M] p.41, §4.6.4 | Высокая |
| A4 | `BestScore` — ненадёжный селектор: застревает на субоптимальных планах (один случайный плохой score → план навсегда отброшен). Использовать только вместе со случайным элементом (`ChangeExpBeta`). | [M] p.40, §4.6.3 | Высокая |
| A5 | MSA-сглаживание (`fractionOfIterationsToStartScoreMSA`) применять вместе с отключением инноваций для форсированной сходимости score. | [M] p.108, §14.3.3 | Высокая |
| A6 | Максимальное количество планов у агента по умолчанию = **5** (`maxAgentPlanMemorySize`). Удаляется план с наименьшим score. | [M] p.40, §4.6.2.4 | Высокая |

## Категория Q: QSim — мобильная симуляция

| # | Правило | Источник | Уверенность |
|---|---------|----------|------------|
| Q1 | `flowCapacityFactor` и `storageCapacityFactor` **должны соответствовать доле выборки**. 10% выборка → оба = 0.1. | [M] p.36, §4.4.1 | Высокая |
| Q2 | `stuckTime` = через сколько **секунд** неподвижности ТС принудительно проходит перекрёсток. По умолчанию = 10 (шагов ≈ секунд). Увеличение ухудшает соответствие счётчикам. | [M] p.36–37, §4.4.1 | Высокая |
| Q3 | **`endTime` критичен**: без него QSim работает пока все агенты не завершат маршрут. При дедлоке (≥1 застрявший агент) симуляция не завершится. Всегда ставить `endTime` (например `30:00:00`). | [M] p.36, §4.4.1 + опыт проекта | Высокая |
| Q4 | Количество потоков QSim — самый чувствительный параметр производительности. Отправная точка: число ядер CPU, оставив один для ОС. | [M] p.34–35, §4.3.2 | Высокая |
| Q5 | Динамика `queue`: ТС не может въехать в звено, если ёмкость заполнена. Режим `withHoles` добавляет upstream-волны со скоростью **15 км/ч** (типичная кинематическая волна). | [M] p.36, §4.4.1 | Высокая |
| Q6 | В сниженных выборках: снижать `passengerCarEquivalents` (PCU) PT-транспорта пропорционально коэффициенту выборки, чтобы избежать артефактов пропускной способности. | [M] p.96–97, §13.6 | Высокая |

## Категория S: Функция оценки Charypar-Nagel

| # | Правило | Источник | Уверенность |
|---|---------|----------|------------|
| S1 | **Дефолтные параметры:** `βperf = +6 util/h`, `βlate = −18 util/h`, `βwait = 0`, `βm = 1 util/деньги`, `βtrav = −6 util/h` (дефолт для всех модов, часто переопределяется). | [M] p.110, §14.4, eq.14.10 | Высокая |
| S2 | Соотношение **βlate / βperf = 3** (т.е. −18 при βperf = 6) — из модели Викри. Не менять без веских причин. | [M] p.110, §14.4 | Высокая |
| S3 | `βwait` оставлять = 0. Ожидание уже неявно штрафуется через opportunity cost времени (βperf). | [M] p.101–102, §14.2.3 | Высокая |
| S4 | `βearly.dp` и `βshort.dur` оставлять = 0 без специальных данных для калибровки. | [M] p.102–103, §14.2.3 | Высокая |
| S5 | Приоритет активности `prioq` оставлять = **1.0**; другие значения никогда системно не исследовались. | [M] p.101, §14.2.3 | Высокая |
| S6 | Полезность активности **логарифмическая**: `Sdur = βperf · ttyp · ln(tdur/ttyp) + const`. Ноль при `tdur = ttyp · exp(−1/prio)`. | [M] p.101, §14.2.3, eq.14.4 | Высокая |
| S7 | MATSim объединяет последнюю и первую активности в одну 24-часовую. Если они разного типа — результаты некорректны (предупреждение в логе). | [M] p.105, §14.2.6 | Высокая |
| S8 | Дезутилита поездки: `Strav = Cmode + βtrav·ttrav + βm·∆m + (βdist + βm·γdist)·dtrav + βtransfer·xtransfer`. | [M] p.103, §14.2.4, eq.14.5 | Высокая |
| S9 | `utilityOfLineSwitch` (βtransfer) = −1.0 по умолчанию. Применяется один раз за пересадку PT (не за плечо). | [M] p.104, config | Высокая |
| S10 | `monetaryDistanceRate` — в **денежных единицах на метр** (не на км!). Должно быть **отрицательным**. Пример: 18 т/км = −0.00018 €/м. | [M] p.104, §14.2.4 | Высокая |
| S11 | `dailyMonetaryConstant` = фиксированные суточные расходы (проездной). `dailyUtilityConstant` = фиксированная суточная утилита. Применяются если мод использован хотя бы раз. | [M] p.104, §14.2.4 | Высокая |
| S12 | Формула VTTS: `VTTS = (−βtrav + βperf) / βm` при типичной длительности. С дефолтами: `VTTS = (0 + 6) / 1 = 6 денег/час`. | [M] p.106, §14.2.7 | Высокая |

## Категория C: Калибровка scoring

| # | Правило | Источник | Уверенность |
|---|---------|----------|------------|
| C1 | **Без оценённой модели выбора**: `βm = 1`, `βperf = +6`, `βtrav,car = 0` (авто штрафуется неявно через opportunity cost), все `βtrav = 0`, затем калибровать модовый сплит через **ASC** (`constant` в `modeParams`). | [M] p.112, §14.4 | Высокая |
| C2 | **С оценённой logit-моделью**: `βm = γденьги` из модели, `βperf = |γin-veh,авто|` (смена знака), `βtrav,авто = 0`, остальные моды — относительно авто. | [M] p.111, §14.4 | Высокая |
| C3 | **ASC пешехода должен быть = 0.0** (`constant = 0.0` для walk). ASC walk суммируется на каждое пешее плечо, включая подходы к остановкам PT. | [M] p.112, §14.4, fn.5 | Высокая |
| C4 | Калибровка **модового сплита**: менять `constant` мода → прогнать итерации → проверить результат → повторить. Итеративно. Инновации отключать достаточно рано, особенно для малых долей. | [M] p.112, §14.4 | Высокая |
| C5 | Если модовый сплит верный, а **распределение расстояний** нет — сначала проверить скорости модов (часто эффективнее, чем βtrav или βdist). | [M] p.113, §14.4 | Высокая |
| C6 | MATSim **концентрирует** поездки на чуть лучшем варианте внутри бина расстояния (не плавный logit). Это известный артефакт механизма удаления планов. | [M] p.113, §14.4 | Высокая |
| C7 | Утилита денег зависит от дохода (подход VSP): `βm(y) = (ȳ/y) · βm0`. Богатые менее чувствительны к стоимости, охотнее платят за скорость. | [M] p.113, §14.4 | Высокая |

## Категория R: Replanning и выбор мода

| # | Правило | Источник | Уверенность |
|---|---------|----------|------------|
| R1 | **`SubtourModeChoice`** нужен когда агент может использовать **несколько модов в течение дня** (авто утром, пешком на обед). `ChangeTripMode` — только один мод для всего плана; `ChangeSingleTripMode` — меняет одно случайное плечо. | [M] p.39, §4.6.2.3 | Высокая |
| R2 | `SubtourModeChoice` + `chainBasedModes = car`: агент может взять авто в суб-туре только если авто было доступно в начале суб-тура (гарантирует возврат авто домой). | [M] p.39, §4.6.2.3 | Высокая |
| R3 | `ChangeExpBeta` — переход на другой план с вероятностью пропорциональной `exp(ΔScore)`. Рекомендуемый стохастический селектор (эмулирует MNL). | [M] p.40, §4.6.3 | Высокая |
| R4 | `SwissRailRaptor` — **дефолтный PT-роутер** с MATSim release 13. Быстрее и реалистичнее старого Dijkstra-PT. | [M] p.96, §13.5 | Высокая |
| R5 | `fractionOfIterationsToDisableInnovation = 0.8` — отключить инновации на последних 20% итераций. | [M] p.41, §4.6.4 | Средняя |

## Категория N: Сеть (атрибуты звеньев)

| # | Правило | Источник | Уверенность |
|---|---------|----------|------------|
| N1 | Атрибуты звена: `capacity` — **ТС/час**, `freespeed` — **м/с** (не км/ч!), `length` — **метры**, `lanes` — количество полос. | [M] p.23–24, §2.3.1.1 | Высокая |
| N2 | Все координаты в MATSim — в **метрах** в проекционной СК (не WGS84). Для Казахстана: EPSG:32643 (UTM Zone 43N). | [M] p.29, §2.3.4 | Высокая |
| N3 | Звенья сети **направленные** (односторонние). Двусторонняя дорога = два звена в противоположных направлениях. | [M] p.23–24 | Высокая |
| N4 | Конвертация скоростей для `freespeed`: **км/ч ÷ 3.6 = м/с**. Примеры: 60 км/ч = 16.67 м/с, 50 км/ч = 13.89 м/с, 90 км/ч = 25.0 м/с, 120 км/ч = 33.33 м/с. | — | Высокая |

## Категория P: Публичный транспорт

| # | Правило | Источник | Уверенность |
|---|---------|----------|------------|
| P1 | PT требует 3 файла: `transitSchedule.xml` (остановки + расписание), `transitVehicles.xml` (типы ТС + вместимость), `network-with-pt.xml` (автосеть + PT-звенья). | [M] p.92, 99–101 | Высокая |
| P2 | `stopFacility` привязывается ровно к одному `link` (`linkRefId`). ТС может обслужить остановку только двигаясь по этому звену. | [M] p.95, §13.4.2 | Высокая |
| P3 | `isBlocking="true"` — автобус блокирует поток сзади (нет кармана). `isBlocking="false"` — карман или трамвайный путь. | [M] p.95, §13.4.2 | Высокая |
| P4 | Расписание PT — **смещения от первого отправления** (не абсолютное время). Если автобус отправляется в 7:00, а `departureOffset="00:03:00"` на остановке 2 → отправление в 7:03. | [M] p.96, §13.4.2 | Высокая |
| P5 | `awaitDeparture="true"` — ТС ждёт запланированного времени отправления даже при раннем прибытии. Без этого — отправится досрочно. | [M] p.96 | Высокая |
| P6 | PCU автобуса = **3.0** по умолчанию (подтверждается СП РК D4). В сниженных выборках снижать PCU PT-транспорта пропорционально коэффициенту выборки. | [M] p.97, §13.6 + [SP] | Высокая |
| P7 | PT-тарифы: `constant` = плата за поездку (один раз, вне зависимости от пересадок), `monetaryDistanceRate` = покилометровая, `dailyMonetaryConstant` = дневной/месячный проездной. | [M] p.97, §13.7 | Высокая |
| P8 | PT-роутер **расписаниевый** (schedule-based): предполагает соблюдение расписания и достаточную вместимость. Events-based роутер существует, но не в основном коде. | [M] p.97, §13.7 | Высокая |
| P9 | Параметры `transitRouter`: `searchRadius` = радиус поиска остановок от O/D (дефолт 1000 м), `maxBeelineWalkConnectionDistance` = макс. пешая доступность (дефолт 300 м), `extensionRadius` = доп. радиус (дефолт 500 м). | [M] p.99 | Высокая |

## Категория T: Транспортный поток (теория)

*Источник: [G] Горев 2010*

| # | Правило | Источник | Уверенность |
|---|---------|----------|------------|
| T1 | **Фундаментальное соотношение**: `N = q · v`, где N — интенсивность (авт./ч), q — плотность (авт./км), v — скорость (км/ч). Рост плотности снижает скорость нелинейно. | [G] p.74, §2.3 | Высокая |
| T2 | **Уровни обслуживания A–F** (по HCM): A — свободный поток (≤600 авт./ч/полосу), B — устойчивый (≤990), C — устойчивый со снижением скорости (≤1430), D — близко к насыщению (≤1910), E — неустойчивый (≤2250), F — затор. | [G] p.78–79, табл.2.4 | Высокая |
| T3 | При превышении пропускной способности (LOS E→F) восстановление занимает значительно больше времени, чем достижение насыщения. Асимметрия затор/разгрузка. | [G] p.77, §2.3 | Высокая |
| T4 | **Транспортное зонирование**: центр зоны — условная точка (не физический объект), подключённая к сети с учётом средних затрат времени на выезд/въезд. | [G] p.55, §2.3 | Высокая |
| T5 | Правила зонирования: (1) внутри зоны — транспортная доступность, (2) границы по естественным барьерам (реки, ж/д), (3) однородное назначение территории, (4) площадь зоны коррелирует со скоростью передвижения. | [G] p.54–55, §2.3 | Высокая |
| T6 | **Гравитационная модель** распределения корреспонденций: `Qij = vi · dj · a/Cij^k`, k ≈ 2. Коэффициент k калибруется по наблюдениям. | [G] p.105–106, §3 | Высокая |
| T7 | Граф транспортной сети должен быть **связанным**: из любой вершины должен существовать путь в любую другую. | [G] p.52–53, §2.3 | Высокая |
| T8 | **Пешеходная доступность остановки**: `lпд = kнп · kв · [1/(3δ) + lп/4]`, где `kнп = 1.2` (непрямолинейность), `δ` — плотность сети, `lп` — длина перегона. | [G] p.56–57, §2.3 | Средняя |
